# Registro de riesgos y deuda técnica — POS Heladería

**Fecha**: 2026-08-15
**Alcance**: `../pos-backend` (FastAPI + PostgreSQL 16) y `../pos-heladeria` (Angular 21), según
define la [Constitución](../../.specify/memory/constitution.md).
**Método**: lectura directa de código y `grep -rn` sobre ambos repositorios; en el frontend se
corrió además `npm audit --omit=dev` (sin instalar nada nuevo). Toda fila cita fichero y línea.
Este documento **no propone correcciones** (Principio III de la Constitución): es un inventario
de lo que hoy es verdad en el código, para que el negocio decida qué hacer con cada fila y
cuándo. El orden de la tabla es impacto × probabilidad, de mayor a menor riesgo estimado; el
criterio de ordenamiento en sí es un juicio de quien documenta, no un hecho — los datos de cada
fila (evidencia) sí lo son.

No se marca ninguna fila como `SUPOSICIÓN`: todo lo que sigue quedó confirmado leyendo el código
que efectivamente se ejecuta (no solo comentarios o nombres de función).

## Notas metodológicas

- **No se hallaron secretos ni credenciales hardcodeadas en código fuente** en ninguno de los
  dos repositorios (`grep` dirigido sobre patrones de secreto/contraseña/API key, más lectura de
  `app/core/config.py`, `docker-compose*.yml` y `src/environments/*.ts`). Toda credencial real
  viaja por variables de entorno (`Settings` con Pydantic en el backend) o no existe en el
  frontend (que no embebe ninguna clave propia). El único hallazgo relacionado con credenciales
  es **R8** (valores por defecto documentados en `.env.example`, no un secreto filtrado).
- **El dinero se modela con `Decimal`/`Numeric(12,2)` en toda la cadena** (`Sale`, `SaleItem`,
  `Payment`, `Invoice`) — no se encontró aritmética de dinero en punto flotante. El frontend solo
  formatea (`shared/money.ts`) el valor que ya llega calculado del backend.
- **El motor de inventario (`inventory/stock.py`) y el consecutivo de facturación
  (`invoices/service.py:_next_number`) están correctamente protegidos** con
  `SELECT ... FOR UPDATE` (incluido orden canónico de ids para evitar deadlocks en
  `lock_items`), y `orders/checkout.py` (`confirm_order`/`block_order`) hace lo mismo sobre el
  pedido. Se documentan como contexto negativo relevante: no todo el código comparte el mismo
  nivel de disciplina de concurrencia (ver R1, R7, R12, R16, R22).
- Este documento no repite hallazgos ya registrados como "zonas oscuras" en
  [`mapa-sistema.md`](./mapa-sistema.md) (ej. `initialize_database()` llamado dos veces, el
  modelo `BusinessHours` huérfano) salvo que aporten una lectura de riesgo nueva.
